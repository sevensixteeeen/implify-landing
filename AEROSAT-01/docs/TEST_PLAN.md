## 1. Scope

Automated verification of: physics calculations, flight-event detection, sensor simulation, telemetry integrity, data recording, playback, and dashboard consistency, plus architecture rules and performance measurement.

## 2. Levels and tooling

| Level | What | Tool |
|---|---|---|
| Unit | One function or class, no I/O | Pytest (backend), Vitest (frontend) |
| Integration | Several modules: full headless run, server with WebSocket client | Pytest with FastAPI's test client |
| Contract | Backend-generated messages validated by frontend code | Vitest, fixtures produced by the backend |
| Statistical | Noise and multi-seed behaviour, fixed seeds | Pytest |
| Performance | Timing measurements, reported | Pytest (marked `perf`), browser measurement |
| Inspection | Items that cannot be automated sensibly | Review checklist |

Test tiers: **fast** (every commit, target under one minute) and **slow** (multi-seed and performance; on demand and before each milestone).

## 3. Principles

### 3.1 Oracle hierarchy

An oracle is the independent source of the expected answer. In order of preference:

1. **Closed-form mathematics** (e.g. vacuum parabola, terminal velocity).
2. **Independently published values** (standard-atmosphere tables), entered by hand with the source cited.
3. **Invariants** (energy conservation, monotonic sequence numbers, one-way states).
4. **Cross-implementation agreement** (RK4 versus Euler at small steps).
5. **Golden files** — only for regression, only after levels 1–4 pass (§3.5).

A test whose expected value comes from the code under test proves nothing and is not allowed.

### 3.2 Tolerances are fixed in advance

Every tolerance below is set now, before any implementation exists. Changing one later requires a written reason in the commit. Loosening a tolerance to make a failing test pass is not an acceptable reason.

### 3.3 Result integrity

- Results come only from tool output (Pytest/Vitest reports), stored with commit hash, platform and versions.
- A test that cannot run is reported as skipped with a reason, never as passed.
- Statistical tests use fixed seeds, so they are deterministic and cannot pass by luck on a rerun.

### 3.4 Canonical form for determinism checks

Two runs are "identical" when the SHA-256 hashes match for:

- `truth.csv`, `truth_events.json`, `sensors.csv`, `avionics.csv` — byte for byte.
- `telemetry.jsonl` — after removing `mission_id` from each line (the only run-specific field in recorded messages).

`manifest.json` is excluded because it holds wall-clock times and the mission ID.

### 3.5 Golden files

- Generated by one documented command, only from a commit where all oracle-based tests pass.
- Stored with the generating commit hash, scenario and seed.
- A diff in a golden file fails the build until a reviewer accepts the regeneration.
- Backend-generated golden telemetry is also the fixture for frontend tests, so both sides test against the same bytes.

### 3.6 File access

- The standard Python file APIs are the built-in `open` and the modules `pathlib`, `io`, `os`, `shutil` and `tempfile`. No other file-access mechanism is used.
- They are permitted in the outer layers (`recorder`, `playback`, `mission`, `server`, `cli`) and in tests. They are not permitted in `sim`, `sensors` or `avionics` (FR-SIM-12, ARCH-02).
- Tests write only to temporary directories (Pytest's `tmp_path`, or `tempfile`) or to the designated project test locations: `backend/tests/golden/` and the frontend fixtures in `frontend/src/__tests__/`, both changed only by the documented golden-file command (§3.5).
- Tests never write to `data/`, `scenarios/`, `schemas/`, `docs/` or any location outside the project, and never modify files they did not create.

## 4. Physics calculations (PHY)

Test configuration for analytic cases: `m = 15 kg`, `C_d·A = 0.005 m²`, `ρ = 1.225 kg/m³` constant, `g = 9.80665 m/s²` constant, `Δt = 1 ms` unless stated. The density is set explicitly in the constant-density verification scenario as `environment.air_density_kgpm3 = 1.225`; it is not a model default and applies to no other scenario. With these, terminal velocity is

```
v_t = sqrt( 2·m·g / (ρ·C_d·A) ) = 219.1633 m/s
```

Closed-form solutions used as oracles (quadratic drag, constant ρ and g):

```
Upward coast from v0 > 0, until apogee, with φ0 = atan(v0 / v_t):
  v(t)      = v_t · tan( φ0 − g·t / v_t )
  h(t)      = (v_t² / g) · ln( cos(φ0 − g·t / v_t) / cos φ0 )
  t_apogee  = (v_t / g) · φ0
  h_apogee  = (v_t² / (2g)) · ln( 1 + v0² / v_t² )

Fall from rest:
  v(t) = −v_t · tanh( g·t / v_t )
  h(t) = −(v_t² / g) · ln cosh( g·t / v_t )
```

For `v0 = 200 m/s` these give `t_apogee = 16.5314 s` and `h_apogee = 1483.659 m`.

## 5. Flight-event detection (EVT)

**Truth event definitions** (the oracle, from `truth_events.json`): liftoff = first tick with h > h_pad; burnout = end of the thrust table; apogee = tick of maximum h; touchdown = interpolated ground-contact time.

**Tolerances** on detection time minus truth time:

| Event | Allowed window |
|---|---|
| `LIFTOFF` | 0 to +0.10 s |
| `BURNOUT` | −0.10 to +0.15 s |
| `APOGEE` | ±1.0 s |
| `TOUCHDOWN` | 0 to +3.0 s |

| ID | Test | Pass criterion |
|---|---|---|
| EVT-01 | FSM unit test with hand-built sample sequences | Each transition occurs at the expected sample |
| EVT-02 | Debounce | Criterion true for N−1 samples then false: no transition. True for N: transition. |
| EVT-03 | One-way states | Under randomised adversarial inputs (seeded), no backward transition ever occurs |
| EVT-04 | No false liftoff | 60 s on the pad, default noise, seeds 0–99: state stays `PAD_IDLE` |
| EVT-05 | REF-01 with ideal sensors | All events within tolerance; detection never precedes the physical cause by more than the stated window |
| EVT-06 | REF-01 with default noise, seeds 0–99 (slow tier; seeds 0–9 in fast tier) | Every seed within tolerance for every event; distribution of errors reported |
| EVT-07 | Apogee lock-out | A pressure spike injected during `BOOST` does not trigger `APOGEE` |
| EVT-08 | Event uniqueness and order | Each event exactly once, in the order LIFTOFF, BURNOUT, APOGEE, DRAG_DEVICE_DEPLOYED, TOUCHDOWN |

## 13. Entry and exit criteria, reporting

- **Entry to Phase 2 testing:** this plan approved; tolerances frozen; reference hardware named (D-9).
- **Build order follows test order:** physics tests pass before sensors are built on top; sensors before avionics; and so on. Golden files are generated only after the oracle-based tests of that layer pass.
- **Exit:** all fast- and slow-tier tests pass on the reference platform; performance measurements reported; any deviation recorded with its reason.
- **Report contents:** commit hash, platform (reference machine per D-9: model, CPU, GPU, RAM and operating-system version, recorded at measurement time), Python/Node/browser versions, pass/fail/skip counts, performance measurements, and the multi-seed error distributions from EVT-06 and EVT-10.
